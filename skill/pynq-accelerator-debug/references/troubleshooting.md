# 故障定位与证据

| 触发条件/现象 | 先收集什么 | 下一步 | 判定依据 |
|---|---|---|---|
| 浏览器打不开 Jupyter | 串口启动日志、`ip -4 addr`、服务监听端口 | 核对 PS 网口、同网段、DHCP、镜像服务 | 分别检查IP连通性和HTTP服务 |
| import pynq 失败 | Python 路径、镜像版本、内核名称 | 切换板端正确内核/适配镜像 | 确认Python内核及PYNQ包路径 |
| 找不到 IP 或没有驱动 | ip_dict、bit/hwh 构建来源、IP VLNV | 核对同次构建元数据、实际层级 IP 名称 | 不自动选择“第一个 DMA” |
| 重复下载后 DMA channel not started | 是否复用已实例化 DMA 的 Overlay、通道状态 | 使用 `ol = Overlay(bitfile, download=True)` 新建对象，再重新取 DMA 驱动 | 本次领航者 PYNQ 2.7.0 实际出现；不推断所有版本都相同 |
| 请求长度被拒绝 | dtype、shape、nbytes、HWH length width | 缩小包长或重新构建长度配置 | 先明确长度单位为字节 |
| DMA 超时 | MM2S/S2MM 状态、长度、设计连接图 | 检查 TLAST、TKEEP、TVALID/TREADY、启动寄存器、时钟/复位，必要时 ILA | 结合状态与波形确认阻塞位置 |
| 短包/接收长度不符 | 实际 S2MM_LENGTH 与参考字节数 | 检查过早 TLAST、输出规格及数据打包 | 收到长度与完整输出契约一致后再比较数值 |
| DMA internal/slave/decode error | status 的 0x10/0x20/0x40 位及 HWH | 结合长度、地址映射、DDR 可达性定位 | 状态位是分类线索，不唯一确定原因 |
| 数值不同但传输完成 | 首个差异、shape、dtype、误差、源数据 | 检查字节序、布局、符号、量化、缓存、算法 | 不临时放宽容差掩盖问题 |
| 超时后 reset 失败 | 失败状态、reset 轮询结果 | 保持 Notebook 内核及隔离缓冲区，复位/重启板卡，再重新加载 Overlay | 不释放仍可能被 DMA 使用的内存 |
| master启动前拒绝idle/auto_restart | 控制协议、初始状态、是否另有进程控制 | 停止新调用，确认所有者及控制语义 | 不把忙碌加速器强制改为空闲 |
| master完成超时 | 最后控制值、指针/标量契约、DDR互联、时钟/复位 | 保留缓冲区并恢复板卡；排查长度、地址可达性和完成语义 | 无DMA TLAST；没有通用复位寄存器 |
| master输出全零或部分未写 | 输出哨兵、独立参考、n与容量、算法模式 | 检查实际执行及写回范围，必要时ILA | 同时检查完成状态与输出参考 |
| 下载Overlay后Qt黑屏 | 是否替换了LCD/VDMA/PWM逻辑、驱动绑定 | 使用配套整机设计，按部署指南停用/恢复外设 | 检查显示链路中的IP及驱动状态 |

定位记录包含现象、候选原因、验证步骤和确认原因，附对应日志、设计或ILA证据。

## 可复现的验证来源

- 软件测试构造超时、错误位、提前结束短包及不停止的 DMA，验证报告与缓冲区处理。
- 厂商例子的流FIFO为发送数据提供缓存，本包采用接收先行，提前准备接收端。
- DMA失败后，先确认停止；master或DMA未确认停止则先恢复板卡。之后在独占条件下新建Overlay。DMA reset不保证加速器本身已清除残留状态。

完整案例见 [重复下载故障](failure-case.md)。
