# Linux／Qt／PL 部署扩展指南

本指南给出Linux／Qt接入PL的部署流程和验收步骤。PYNQ运行在Linux上，Jupyter用于调试，Qt通过后台服务调用推理。

可运行的最小整机案例见 [Qt 触摸联调页](../examples/qt_demo/README.md)：选择 FIFO 或仿射、设置长度、触摸运行、查看全数组比对与调用耗时。Qt、任务服务与输入参考可复用；显示驱动、800×480 分辨率和 GT911 配置集中在 [领航者7020板卡附录](qt-navigator7020.md)。

## 先选已有系统还是迁移系统

| 路线 | 优先适用条件 | 必须处理的工作 |
|---|---|---|
| 沿用原 Linux＋Qt | 显示/触摸和现有驱动已经稳定 | 保持整机硬件与设备树配套，接入现有 C/C++ 推理运行时；复用本包参考、报告和排错方法 |
| 迁移到本板 PYNQ 镜像 | 需要 Python 控制与交互式调试，且接受迁移成本 | 核对显示驱动、Qt库及平台插件、触摸节点、设备树、内存、服务启动和依赖 |

原Linux系统可以复用参考比对和报告工具。选择PYNQ路线时，一起核对FPGA管理、连续内存分配和设备驱动。

## 目标架构

```text
Qt 主线程：显示、输入、状态刷新
        ↕ 任务ID／状态／结果（本地IPC或现有HTTP接口）
后台推理服务：排队、输入校验、参考版本、错误与日志
        ↕ 单一硬件所有者
运行时：C++现有驱动，或已适配的PYNQ调用
        ↕ 寄存器＋受管理的DDR缓冲区
整机PL：AI计算＋显示所需逻辑＋其他必须保留的外设
```

PL等待放在后台工作线程或服务中，Qt主线程负责交互。沿用项目已有IPC或HTTP协议，每个加速器由一个进程独占；Notebook调试与服务运行分时进行。

## 阶段1：核对整机配套

| 材料 | 检查 | 失败表现或后果 |
|---|---|---|
| FPGA完整设计 | AI、LCD/VDMA、PWM、触摸相关逻辑是否同时存在，地址是否冲突 | 下载只含AI或FIFO的完整位流可能使显示消失 |
| FSBL/启动配置 | PS DDR、MIO、时钟与板型、硬件导出一致 | Linux未启动、网口或DDR不稳定 |
| 位流/HWH/设备树 | 来源和硬件接口一致，Linux驱动绑定真实设备 | 错误地址访问、驱动等待或启动失败 |
| 内存 | 固定预留区与CMA、显示帧缓存、Linux可用内存不重叠 | 内存损坏或分配失败 |
| 运行时与模型 | 硬件身份、寄存器ABI、权重打包及量化一致 | 同尺寸数据也可能算错 |
| Qt | ARM架构、动态库、平台插件与已有启动参数匹配 | 程序无法加载或没有显示 |
| 触摸 | 当前输入节点、驱动、坐标映射和权限 | 显示正常但触摸失效 |

DMA回环位流只用于专用测试。加载整片 Overlay 会替换 PL；若正在运行显示驱动，必须先按该系统的外设停用/重新绑定流程处理。没有已验证的动态重配置流程时，优先用配套整机启动包冷启动，不在活动显示链路下热切位流。

只读取证可从 `/proc/device-tree`、`/proc/iomem`、`/proc/meminfo`、`/sys/class/graphics`、`/proc/bus/input/devices`、启动日志和构建清单入手。显示也可能用 DRM 而非 `/dev/fb0`，节点名称必须由当前系统确认。

## 阶段2：单次真实计算

先不开 Qt 业务调用，用最小输入完成一次 IP 身份检查、模型加载、输入传输、PL执行、输出与独立参考比对。记录 dtype、布局、量化、模型版本和完成状态。随后验证代表输入、边界、数值错误和恢复。

固定预留内存运行时先检查设备树与内核内存映射，确认该区域专供PL。迁移到allocate时，更新所有设备指针和工作区布局，并检查CMA容量及输出缓存同步。

## 阶段3：后台服务

最小任务契约建议包含：`task_id`、输入规格/版本、状态（queued/running/complete/failed）、真实进度、输出、计时边界和错误。沿用现有字段时保持兼容。

- 一次只有一个硬件所有者；上传队列与内存容量有上限。
- 校验输入长度、版本和数值；失败任务返回明确的错误状态及原因。
- 客户端断线可按原任务查询；不因页面刷新重新启动同一推理。
- 取消任务先区分“停止排队”和“中断已在PL执行”；没有安全停止协议时只停止后续调度，并等当前硬件安全结束。
- 超时进入错误状态并保留报告；只有硬件已确认停止，服务才能回收缓冲区和接受新任务。

## 阶段4：Qt接入和共存

Qt 显示服务提供的实际任务状态，不靠固定定时器伪造进度。任务期间检查触摸响应、图像更新、网络收发和内存占用；分别记录纯推理运行时与用户点击到结果显示的耗时。

至少验证：一次正常任务、一次错误输入、一次客户端断线重连、连续多次任务，以及退出界面时后台仍运行的策略。PL超时可先用模拟后端注入，记录测试使用的后端。

## 阶段5：开机启动和回退

按系统实际使用的systemd、SysV或厂商脚本集成启动项。依赖顺序为：硬件和驱动就绪→内存/模型/身份检查→推理服务就绪→Qt显示业务状态。服务启动前检查硬件所有权。

冷启动验收：串口启动正常、显示/触摸可用、服务就绪、完成新任务、结果版本正确、报告可保存。断电再启动后运行一次新任务，保存对应日志。

保存旧启动包、配套说明和业务数据备份。BOOT、内核、设备树、rootfs、运行时与模型按项目的配套关系一起更换。从PYNQ卡恢复其他系统时，先核对当前分区和启动链，再决定恢复方式。

## 将指南应用到自己的项目

在接口表中填写实际模型/算法、寄存器 ABI、权重或参数布局、内存来源及整机启动材料。固定预留 DDR 的地址和容量取自本项目的设备树与链接/分配配置；使用 PYNQ allocate 时传入实际分配的设备地址。

本包提供的可运行实例为 FIFO 与仿射双通路。接入自己的 AI 算法时，替换后台服务的输入与参考、运行时调用及必要的模型加载步骤，按 [验收模板](migration-acceptance.md) 保存结果。
